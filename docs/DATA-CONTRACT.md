# 대구 날씨 데이터와 기록 보존 규칙

## 공개 원천과 시간

- 출처: [Open-Meteo Forecast API](https://open-meteo.com/en/docs)
- 위치: 대구 중구 기준 좌표 `35.8714, 128.6014`
- 매일 비교하는 값: `current.temperature_2m`, 지상 2m 현재 기온 `°C`
- 시간대: `Asia/Seoul`, UTC+09:00
- 원천 URL: `public/core.mjs`의 `SOURCE.url` 및 각 실제 기록의 `sourceUrl`
- 보조 정보: 현재 습도·체감온도·강수량·하늘 상태·바람, 앞으로 24시간 기온·강수확률·하늘 상태, 7일 최고·최저기온·강수확률·일출·일몰

현재 기온은 15분 간격 기상 모델 자료에 기반합니다. `current.time`과 정규화한 `observedAt`은 원천 기준 시각이며 특정 관측소 실측 시각을 뜻하지 않습니다. `fetchedAt`은 실제 정상 수신 시각입니다. 현재 값과 미래 예보를 구분하며 예보 날짜를 실제 관찰 날짜로 세지 않습니다. 키·사용자 위치·개인정보를 요청에 넣지 않습니다.

## 정상 응답 검증

HTTP 성공, JSON 구조, 시간대·오프셋, 단위, 유한한 숫자형 기온과 `-80~60°C` 범위, 원천 시각을 검사합니다. 응답 좌표가 있으면 대구 요청점 인근의 모델 격자인지 확인합니다. 원천 기준 시각이 수신보다 2시간 초과 오래되면 새 정상값으로 받지 않고, 5분 초과 미래이면 거절합니다. 요청 제한 시간은 8초입니다. 이 범위와 시간 제한은 앱의 방어 규칙이며 기상 정확성을 보증하지 않습니다.

보조 날씨와 예보는 항목별 단위·값·시각·배열 길이를 따로 검증합니다. 예보가 잘못되거나 비어도 유효한 현재 기온을 버리지 않습니다. 해당 예보에 자료 없음·형식 오류 안내를 표시하며 실제 기록은 보존합니다.

## 실제 기록 형식

`public/data/observations.json`의 상태 버전은 `2`입니다. 비어 있을 때 `{ "version": 2, "lastGood": null, "days": [] }`이며 `lastGood`과 `days`의 기록은 다음 필드를 사용합니다.

| 필드 | 의미 |
| --- | --- |
| `value` | 정규화한 실제 기온 숫자 |
| `unit` | `°C` |
| `sourceId` | `open-meteo-daegu` |
| `sourceUrl` | 해당 대구 조회의 고정 공개 원천 URL |
| `observedAt` | 원천 기준 시각, `+09:00` ISO 문자열 |
| `fetchedAt` | 실제 수신 시각, UTC ISO 문자열 |
| `kstDate` | 실제 수신 시각을 KST로 환산한 날짜 |
| `kind` | `real` |

`kind: real` 표기 자체가 실제 조회의 증거는 아닙니다. 수집 실행·응답 원문·원문 SHA-256·저장값을 함께 확인합니다. 실제 수집은 시스템 현재 시계와 고정된 대구 API를 쓰며 합성 fixture와 날짜 덮어쓰기 입력을 받지 않습니다.

첫 실제 대구 수집은 **2026-09-22 09:36:25.628 KST, 21.9°C**, 원천 기준 시각은 **09:30 KST**입니다. [원문 응답](../public/data/evidence/2026-09-22T00-36-25.628Z.json)의 SHA-256은 `039709bb02d857463203c022cba81903394c325f9963137cbdb00440c161fa2e`입니다. 과거 서울 자료는 `docs/archive/seoul-prototype/`에 보관하며 대구의 실제 날짜 기록에 포함하지 않습니다.

## 일별 갱신과 어제 대비

1. `sourceId + kstDate`를 일별 고유키로 사용합니다.
2. 같은 KST 날짜에 더 최근 정상 조회가 성공하면 기존 한 행을 갱신합니다. 오래된 응답으로 되돌리지 않습니다.
3. 다음 KST 날짜의 성공은 새 행을 하나 추가합니다. `lastGood`은 가장 최근 정상 일별 행과 일치해야 합니다.
4. 실패하면 정상값·일별 행을 수정하지 않습니다. 마지막 정상값과 오래된 값 표시, 실패 종류, 다음 행동을 보여 줍니다.

`하루에 한 줄`의 전날 대비는 달력상 오늘의 `value - 어제 value`입니다. 양쪽 중 하나가 없으면 비교 불가라고 설명합니다. 가장 가까운 과거 날짜를 달력상 어제로 바꾸지 않습니다. 기온은 API 정밀도로 보존하고 부동소수점 계산 오차를 정리한 후 표시합니다.

## 심사용 실제 두 날짜 보존

`public/data/review-evidence.json`은 실제 서로 다른 KST 날짜의 보관 자료를 **최대 두 건** 유지합니다. 각 항목은 `{ reading, evidencePath }`이며 그 날짜의 첫 보관값과 원자료 경로를 고정합니다. 같은 날 후속 수집으로 갱신되는 `observations.json`과 별도이므로 제출 대조 시점의 값이 바뀌지 않습니다. 둘째 실제 날짜가 없으면 1/2일 및 비교 불가를 표시합니다.

공식 C22~C24 판정에는 플랫폼 `t04_day` 봉인 영수증 정확히 2건이 필요합니다. 두 `server_created_at`의 KST 날짜, payload의 `source_url`·`source_observed_at`·`normalized_value`·`unit`을 앱의 보관 자료 및 화면값과 대조합니다. 보관 자료의 날짜별 값이 실제 플랫폼에 기록한 값과 다르면 임의로 일치했다고 표시하지 않습니다. 사용자는 플랫폼 날짜 기록 화면을 아직 확인하지 않았다고 답했으며 영수증 존재·내용은 미확인 상태입니다. 플랫폼 영수증은 앱에서 생성하거나 위조하지 않습니다.

일별 표의 비교는 최근 정상값끼리, 심사용 보관 표의 비교는 보존한 두 값끼리 계산합니다. 두 보관 날짜가 연속하지 않으면 이를 두 기록 간 변화로 설명하며 달력상 어제 대비로 표시하지 않습니다. 실제 영수증 대조는 별도 확인이 필요합니다.

## 저장 영역

| 영역 | 목적 | 실제 대구 이틀 증거 |
| --- | --- | --- |
| 공개 `observations.json` | 같은 날짜 최근 정상값을 갱신하는 공통 일별 기록 | 실제 수집 근거를 대조한 경우만 |
| 공개 `review-evidence.json` | 심사 시 대조할 실제 날짜별 두 보관값 | 실제 수집 근거를 대조한 경우만; 플랫폼 영수증과 별도 |
| 공개 `data/evidence/` | 실제 원문·조회 시각·정규화 값·SHA-256 보관 | 대구 실수집 근거 |
| 방문자 브라우저 저장소 | 이 브라우저의 실제 조회 기록 | 공통 공개 증거에 합산하지 않음 |
| 합성 adapter의 메모리 상태 | 공식 fixture 재생 | 포함하지 않음 |
| 서울 시제품 보관 자료 | 과거 작업 추적 | 포함하지 않음 |

브라우저 저장 차단·손상·미래 시각 자료는 경고 또는 격리하며 성공으로 꾸미지 않습니다. 합성 초기화는 합성 평가 상태만 비웁니다. 새 시크릿 창에서도 공통 공개 자료를 볼 수 있어야 합니다.

## 공식 합성 실패와 회복

[공식 꾸러미](../public/assets/t04-real-information-board-public-v1/README.md)의 원본 바이트를 보존합니다. package ID는 `aleph-t04-real-information-board-public-contract-v2`, public contract는 2.0.0, fixture contract는 1.1.0입니다.

| fixture | 실패 상태 | 다음 행동 |
| --- | --- | --- |
| `T04-TIMEOUT` | `stale / timeout` | 잠시 후 다시 시도 |
| `T04-AUTH-401` | `stale / auth` | 외부 원천의 공개 접근 정책 확인 |
| `T04-RATE-429` | `stale / rate_limit` | 원천이 안내한 대기 후 다시 시도 |
| `T04-OFFLINE` | `stale / offline` | 인터넷 연결 복구 후 다시 시도 |
| `T04-SCHEMA-BREAK` | `stale / schema_error` | 원천 응답 형식과 변환 규칙 확인 |

각 실패는 합성 초기화→D1-A(100)→D1-B(105) 후 재생합니다. 실패 뒤 105와 일별 한 행을 보존합니다. timeout 후 다시 시도로 `T04-RECOVER-D2`를 적용하면 `fresh / none`, 120, 다음 합성 날짜 신규 한 행, 총 두 행이 됩니다. D1-A→D1-B는 같은 record ID를 유지하면서 100→105로 갱신하고 D2는 120·변화 절대값 15를 만듭니다.

fixture의 2026-08-24/25는 합성 날짜이며 실제 관찰 기간과 무관합니다. 실제 원천·공개 일별 자료에 fixture를 저장하지 않습니다. 외부 원천의 401/403 합성은 결과물 로그인이나 인증을 허용한다는 뜻이 아닙니다.

## 공개와 자동 수집

매일 09:20 KST GitHub Actions 수집을 예약합니다. 실제 `fetchedAt`을 기록 날짜로 사용하며 예약 실행은 지연될 수 있습니다. 실패한 날에는 과거 정상값을 새 날짜로 복사하지 않습니다. 정상 수집의 원문·일별 값·심사용 자료를 저장소에 반영하고 빌드·배포 후 공개 자료를 다시 대조합니다.

소스 제출 URL은 검증한 배포에 대응하는 전체 커밋으로 고정합니다. 공개 자료·브라우저·응답·Git 이력에 비밀값이나 개인정보를 넣지 않습니다. 플랫폼에는 주소·확인법·판단만 입력하고 별도 증거 ZIP을 필수 첨부물로 추가하지 않습니다.
