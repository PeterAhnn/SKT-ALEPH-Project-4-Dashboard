# 데이터와 기록 보존 규칙

## 공개 원천

- 원천: Open-Meteo Forecast API의 현재 지상 2m 기온
- 위치: 서울 중구 기준 좌표 `37.5665, 126.9780`
- 단위·시간대: `°C`, `Asia/Seoul` / UTC+09:00
- 출처 설명: [Open-Meteo 공식 문서](https://open-meteo.com/en/docs)
- [현재 조회 URL](https://api.open-meteo.com/v1/forecast?latitude=37.5665&longitude=126.9780&current=temperature_2m&timezone=Asia%2FSeoul&forecast_days=1)

현재 값은 15분 간격의 기상 모델 자료를 기반으로 합니다. `current.time`은 원천 자료의 기준 시각입니다. 코드의 `observedAt`이라는 필드명도 이 기준 시각을 뜻하며 특정 관측소에서 실측한 시각이라는 의미가 아닙니다. API 키나 사용자 위치 정보는 보내지 않습니다.

## 정상 응답의 조건

응답이 성공 상태여야 하며 JSON 구조, 숫자형 기온, 단위, 시간대, 기준 시각을 검사합니다. 기온이 유한한 숫자이고 `-80~60°C` 범위인지 확인합니다. 범위 검사는 앱의 방어 규칙이며 원천 정확성을 보증하지 않습니다.

원천 기준 시각이 수신 시각보다 2시간 넘게 오래되면 `stale`, 5분 넘게 미래이면 `invalid`로 처리합니다. 기본 요청 제한 시간은 8초입니다. 이 임계값들은 구현 기본안이며 공식 과제 카드와 대조가 필요합니다.

## 저장 형식

공개 파일은 `public/data/observations.json`이며 최상위 구조는 다음과 같습니다. 다음은 기록이 없는 상태의 구조 설명용 예시이고, 현재 실제 파일 내용은 아닙니다.

```json
{
  "version": 1,
  "lastGood": null,
  "days": []
}
```

`lastGood`과 `days`의 각 실제 기록은 같은 필드를 사용합니다.

| 필드 | 의미 |
| --- | --- |
| `value` | 원천이 반환한 기온 숫자 |
| `unit` | `°C` |
| `sourceId` | `open-meteo-seoul` |
| `observedAt` | 원천 기준 시각, `+09:00` 오프셋이 있는 ISO 문자열 |
| `fetchedAt` | 정상 수신 시각, UTC의 ISO 문자열 |
| `kstDate` | `fetchedAt`을 KST로 환산한 날짜 `YYYY-MM-DD` |
| `kind` | 실제 원천 기록의 `real` 표시 |

`kind: real` 문자열만으로 실제 조회가 입증되는 것은 아닙니다. 실제 수집 실행, 원천 응답 및 저장 파일을 대조해야 합니다. 날짜나 값이 들어 있는 예시 기록을 초기 데이터로 배포하지 않습니다.

현재 첫 실제 수집은 2026-09-22 09:14:21 KST, 19.5°C입니다. 원천 응답과 SHA-256을 `public/data/evidence/2026-09-22T00-14-21.391Z.json`에 보관했습니다. 원천 기준 시각은 같은 날 09:00 KST입니다. 요청 좌표와 모델 격자 좌표는 다를 수 있으며 첫 응답의 좌표는 `37.55, 127.0`입니다.

같은 날 GitHub Actions의 실제 후속 수집은 09:19:28 KST, 20°C·원천 기준 09:15 KST입니다. 근거는 `public/data/evidence/2026-09-22T00-19-28.655Z.json`에 있습니다. `lastGood`은 20°C로 갱신되었지만 `days`의 첫 대표값은 19.5°C이고 실제 날짜 수는 1일입니다.

## 하루 대표값과 마지막 정상값

1. 실제 수신 시각을 KST로 환산하여 기록 날짜를 정합니다.
2. 해당 날짜의 첫 정상값을 `days`에 한 번 보관합니다. 같은 날의 후속 조회로 이 대표값을 바꾸지 않습니다.
3. 더 최근 정상 조회는 `lastGood`을 갱신합니다. 실패는 두 필드를 변경하지 않습니다.

일별 기록은 날짜순이며 중복 날짜를 허용하지 않습니다. 어제 비교는 요청한 KST 날짜와 정확히 하루 전 날짜의 대표값을 찾아 `오늘 value - 어제 value`로 계산합니다. 양쪽 중 하나가 없으면 변화값을 표시하지 않습니다. 가장 가까운 과거 날짜를 ‘어제’로 대신하지 않습니다.

실제 두 날짜 관찰에는 서로 다른 KST 날짜에 수집 명령을 실행하여 남긴 기록이 필요합니다. 시스템 날짜 변경, 소급 수집, 과거 자료로 빠진 날짜를 채우기, 합성값 사용은 이 요건을 충족하지 않습니다.

## 저장 영역의 구분

| 영역 | 용도 | 공개 관찰 증거로 집계 |
| --- | --- | --- |
| 공개 `observations.json` | 실제 수집 명령이 저장하고 배포한 공통 기록 | 실제 수집 근거를 확인한 경우만 |
| 브라우저 로컬 저장소 | 해당 방문자가 실제 조회한 기록의 편의 보존 | 아니요 |
| 합성 재생 상태 | 실패 처리 검증과 설명 | 아니요 |

심사자는 새 시크릿 창에서도 공개 파일의 같은 기록을 확인할 수 있어야 합니다. 브라우저 저장이 차단되거나 손상되면 이를 알리고 공개 기록을 훼손하지 않습니다. 공개 파일을 불러오지 못한 상황도 ‘기록이 없는 상태’와 구분해 설명해야 합니다.

## 자체 실패 재생 초안

| 코드 | 합성 입력 | 기대 동작 |
| --- | --- | --- |
| `network` | 연결 예외 | 연결 실패 이유와 재시도 안내 |
| `timeout` | 제한 시간 동안 미응답 | 응답 지연 안내 |
| `http` | HTTP 503 | 서버 오류 안내 |
| `invalid` | 기온이 숫자가 아닌 응답 | 잘못된 응답을 새 정상값으로 저장하지 않음 |
| `stale` | 기준 시각이 3시간 오래된 응답 | 오래된 자료를 새 정상값으로 저장하지 않음 |

모든 재생은 실제 조회와 같은 응답 검사 경로를 사용하되 저장 영역을 분리합니다. 성공처럼 보이는 합성값도 실제 기록에 추가하지 않습니다. 검사의 기대 결과는 기존 정상값·일별 기록 보존이며, 실행 결과가 있어야 통과로 표시합니다.

공식 상세 카드와 합성 검사 꾸러미는 미수령 상태입니다. 위 다섯 종류를 공식 지정 목록으로 주장하지 않으며, 수령 후 정상 흐름까지 함께 대조합니다.

## 변경과 공개

실제 수집 파일이 바뀌면 빌드·배포를 갱신하고 공개 화면과 원본 파일을 대조합니다. 소스 제출 URL은 검증한 배포와 일치하는 전체 커밋으로 고정합니다. 공개 자료에는 개인정보·비밀번호·토큰·비밀 API 키를 넣지 않습니다. 날짜·해시·과제 버전을 플랫폼 입력란에 별도 증거 항목으로 덧붙일 필요는 없습니다.

GitHub Actions의 `.github/workflows/daily.yml`에 매일 09:20 KST 수집 일정을 연결했습니다. 예약 실행은 지연될 수 있으므로 실제 `fetchedAt`을 기록 날짜의 근거로 사용합니다. 정상 수집은 원천 응답과 기록을 함께 커밋하고 연결된 Vercel이 배포합니다. 실패하면 과거 정상 기록을 새 날짜로 복사하지 않습니다.

[첫 수동 실행](https://github.com/PeterAhnn/SKT-ALEPH-Project-4-Dashboard/actions/runs/35671454459)과 연결 운영 배포는 성공했습니다. [공개 정보판](https://skt-aleph-project-4-dashboard.vercel.app)과 전체 커밋 소스는 새 격리 브라우저에서 인증 없이 열렸습니다. 배포된 `index.html`, `app.mjs`, `core.mjs`, `style.css`, `data/observations.json`의 SHA-256은 커밋 `37ac8914ad7a0e7c91ff79c91402c6c7ba7e3893`의 각 파일과 일치했습니다. 근거는 [공개 접근](verification/public-source-access.json)과 [파일 해시](verification/public-file-hashes.json)에 보관합니다. 다음 실제 날짜의 예약 실행·공개 기록 반영·변화값은 아직 확인하지 않았습니다.
